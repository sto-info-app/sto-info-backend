## Project Overview

The `sto-info-backend` is a NestJS-based REST API that powers the STO Info platform. It provides structured, secure endpoints for player accounts, characters, fleets, authentication, and related operational data. This backend enables the frontend application and integrations to retrieve, validate, and manage Star Trek Online-related information reliably.

## Features

The code is grouped by domain under [src/](src/):

- Accounts and sign-in: users, authentication, refresh tokens, settings, and STO Accounts and Characters
- Fleet Community: Communities, Fleets and Armadas, with governance, recruitment, holdings, events, news, activity, chat, roster imports and roster history
- Friends and blocks between members
- Storytime
- Captain's Log
- Site news
- Notifications, with email delivery through an outbox
- File assets: the registry, upload scanning through the [file scan worker](https://github.com/sto-info-app/sto-info-file-scan-worker), rescan campaigns and private image delivery
- Moderation and user reports
- Custom Tracking
- Site statistics
- Webhooks (Amazon SES)
- The admin audit and Security Log
- Operations: alerts, failed jobs, restore checks, health and diagnostics

## Getting Started

### Prerequisites

- Node.js 24.22.3 or later 24.x (pinned in `.nvmrc`; 24.22.3 is the November 2026 security release)
- npm 11.x (bundled with Node.js 24)
- PostgreSQL 18
- Redis 7.x
- AWS Secrets Manager
- Cloudflare R2 and Cloudflare Images for file storage and delivery (MinIO stands in for R2 locally)
- The [file scan worker](https://github.com/sto-info-app/sto-info-file-scan-worker), which scans uploads with ClamAV, if you work on file uploads

### Installation

1. Clone the repository:

```sh
git clone https://github.com/sto-info-app/sto-info-backend.git
```

2. Navigate to the project directory:

```sh
cd sto-info-backend
```

3. Install the dependencies:

```sh
npm ci
```

> Note: the repository ships an [.npmrc](.npmrc) setting `legacy-peer-deps=true`. It is required — Jest's toolchain sits on Babel 7 while `@stryker-mutator/core@10` instruments through Babel 8, so a strict peer resolution fails with `ERESOLVE`. The flag matches how CI installs (`npm ci --ignore-scripts --legacy-peer-deps`), which keeps the lockfile reproducible. See [docs/security.md](docs/security.md#babel-7-jest-and-babel-8-stryker) for the detail.

### Configuration

Environment files live in [config/environments/](config/environments/):

- [config/environments/.env](config/environments/.env): used for local development (not committed)
- [config/environments/template.env](config/environments/template.env): starting point for creating your local `.env`
- [config/environments/.env.example](config/environments/.env.example): safe example for hosted environments (e.g. Render)

Create a `.env` file by copying [config/environments/template.env](config/environments/template.env) to [config/environments/.env](config/environments/.env), then amend values to match your local setup.

Environment variables and the required AWS Secrets Manager secret shape are documented in [docs/environment-variables.md](docs/environment-variables.md).

### Database

This application uses PostgreSQL. Schema changes are managed with TypeORM migrations.

Database notes (including retention jobs and dev-only seeding) are in [docs/database.md](docs/database.md).

Migration commands are as follows:

```sh
npm run migration:generate -- -n <NameOfMigration>
npm run migration:run
npm run migration:revert
npm run migration:show
```

### Running the Application

Apply any pending migrations, then start the development server:

```sh
npm run migration:run
npm run start:dev
```

`start:dev` does not run migrations, so run `migration:run` again whenever new ones arrive. The server will be running at `http://localhost:3000`.

### Running Tests

To run the tests for this project, use the following command:

```sh
npm test
```

This will execute all the unit tests and provide a summary of the test results.

The end-to-end suite in [test/](test/) runs with `npm run test:e2e`. The `rehearse:*` scripts run migrations and the operations runbooks against throwaway Docker containers; see the [migration rehearsal](scripts/migration-rehearsal/README.md) and [operations rehearsal](docs/operations/rehearsal.md) for what each needs.

### Mutation testing

This project uses Stryker for mutation testing.

```sh
npm run test:mutation
```

In CI the weekly full run is split into 16 shards that run in parallel, each keeping its results between weeks, and a final job merges them into one report. See [Weekly full run](docs/github/QUALITY-AUTOMATION.md#weekly-full-run) for how, and for running a single shard locally.

For PR-style incremental mutation testing (only mutates relevant changed `src/**/*.ts` files), you can run:

```sh
BASE_REF=origin/development npm run test:mutation:incremental
```

### Local verify (CI-style check)

To run the same kind of checks expected by CI (in order: audit, lint, format check, tests with coverage, lightweight fuzz tests, and a build), run:

```sh
npm run verify
```

## Security Testing

### Property-based fuzz testing

This project uses [fast-check](https://github.com/dubzzz/fast-check) for property-based fuzz testing to ensure robustness against unexpected inputs.

**Run locally (lightweight):**

```bash
npm run test:fuzz
```

**Run locally (comprehensive):**

```bash
npm run test:fuzz:full
```

**Customise iteration count:**

Set the `FUZZ_NUM_RUNS` environment variable to control the number of test iterations:

```bash
FUZZ_NUM_RUNS=500 npm run test:fuzz
```

Defaults: `npm run test:fuzz` runs 50 iterations and `npm run test:fuzz:full` runs 1000. A fuzz spec run directly, without either script, falls back to 100.

**CI behaviour:**

- **Pull requests**: Runs lightweight fuzz tests (50 iterations) to catch obvious issues quickly
- **Weekly schedule**: Runs comprehensive fuzz tests (1000 iterations) for deeper analysis

### OWASP ZAP DAST scanning

Dynamic Application Security Testing (DAST) is performed using OWASP ZAP to identify security vulnerabilities in the running API.

**CI behaviour (dev API, `security-zap-dev.yml`):**

- **Development version bumps**: Runs a ZAP baseline scan against the dev API `/health/live` endpoint (using a smart polling loop for up to 10 minutes to wait for deployment)
- **Weekly schedule**: Runs a ZAP full scan against the dev API base URL every Monday at 03:00 UTC
- **Manual trigger**: Can run baseline or full scan via workflow_dispatch

**CI behaviour (production API, `security-zap-prod.yml`):**

- **Production releases**: When a `package.json` change reaches `production` (a version bump or a merged pull request), waits up to 10 minutes for the new version to be deployed, then runs a ZAP baseline scan against the production API `/health/live` endpoint
- **Monthly schedule**: Runs a ZAP full scan against the production API base URL on the 1st of every month at 04:00 UTC
- **Manual trigger**: Can run baseline or full scan via workflow_dispatch

**Both workflows:**

- **WAF Bypass**: Scans and connectivity checks use a custom `User-Agent` to bypass edge protection
- **Scan reports**: Available as workflow artifacts for 30 days

**Limitations:**

- Scans run against unauthenticated endpoints only
- Authenticated endpoints require valid JWT tokens (not currently tested)
- False positives can be tuned via `.zap/rules.tsv`

See [SECURITY.md](SECURITY.md) for more details.

### Deployment

The API runs on Render. Each environment is described by a Render Blueprint in [render/](render/): [development.yaml](render/development.yaml), [staging.yaml](render/staging.yaml) and [production.yaml](render/production.yaml). Every service builds with `npm install; npm run build`.

- Development and staging start with `npm run start:render`, which runs `migration:run` and then `start:prod`.
- Production runs `migration:run` as its pre-deploy command and then starts with `start:prod`.

What runs where, the secrets each service reads and how to sync a Blueprint are in [Render services, secrets and connection budgets](docs/operations/render-services.md). The rest of the [operations runbooks](docs/operations/README.md) cover readiness, alerts, failed jobs, restore, rollback and incidents.

## API Documentation

The API documentation is available at `http://localhost:3000/swagger` once the server is running. This documentation is generated using Swagger, which provides a user-friendly interface to explore and test the API endpoints. Swagger will not be loaded if in Production.
